# 전처리(청킹 포함) 실험 기록: 어떻게 하면 검색 효과가 좋은가

인공지능기본법 RAG(`rag/`)에서 **전처리 방식(청킹 포함)에 따라 검색 효과가 어떻게 달라지는지**를 현재 가진 데이터(법률 1건, 골든셋 43문항)만으로 확인한 기록이다.
처음 만든 방식, 그 뒤에 걱정된 점, 걱정을 숫자로 확인한 실험, 가장 효과가 좋았던 방식을 정리했다.
실험 날짜: 2026-10-08. 코드: `rag/`, 평가: `eval/`. 전체 설계 결정은 [rag_design.md](rag_design.md) 참고.

## 1. 한눈에 보기

| 걱정 | 시도 | 결과 | 채택 |
|---|---|---|---|
| ① 같은 조의 child가 검색 상위를 독점한다 | 조당 child 상한(`cap2`, `cap3`) | 다양성은 늘었지만 정답을 찾는 능력은 그대로 | 안 함 |
| ② 짧은 항이 다른 항을 가리켜 뜻이 불완전하다 | 참조 풀기(`refs`) | 노린 문항이 좋아지지 않았고 오히려 몇 문항이 나빠짐 | 안 함 |
| ③ child 500자 기준이 임의의 값이다 | 300 / 800 / 1200자 비교 | **300자가 가장 안정적** | **함 (기본값 500 → 300)** |

**가장 효과가 좋았던 방식은 child 크기를 300자로 낮춘 것이다.** 정답 조를 상위 3개 안에 넣는 비율이 0.951 → 0.976, MRR이 0.911 → 0.929로 오르고, 어떤 문항도 나빠지지 않았다.
다만 문항이 41개뿐이라 차이는 문항 1~2개 수준이다(6장 한계 참고).

## 2. 처음 구현한 방식

### 입력과 파싱
- 입력은 `data/ai_basic_law/`의 HWPX 파일이었다. HWPX는 zip이고 본문은 `Contents/section0.xml`이다.
- 실제 파일을 열어 보니 조·항·호·목이 별도 태그가 아니라 **일반 문단이고 접두어로만 구분**됐다(`제1조(목적)`, `①`, `1.`, `가.`).
  그래서 접두어 정규식으로 계층을 복원했다. 표 안에 중첩된 문단(표지·머리글)은 최상위 문단만 읽어 제외했다.
- 가지조문(`제17조의2`), 가지호(`4의2.`), 개정 이력(`<개정 …>`, `[본조신설 …]`)도 따로 처리했다.
- 결과는 Canonical Legal JSON(조 → 항 → 호 → 목)으로 저장했다.
- 검증: 조/항/호/목 = 46/164/191/13. HWPX 본문 373줄이 JSON에 빠짐없이 들어 있고 번호도 순서대로 이어졌다.

### 청킹 (Parent-Child)
- **Parent = 조(條) 전체.** LLM에 근거로 넘기는 단위다.
- **Child = 검색(임베딩)하는 단위.** 조가 **500자 이하면 조 전체를 child 하나**로 하고, 길면 항 → 호 → 목 순으로 필요한 만큼만 쪼갠다.
  쪼갤 때 상위 문장(항·호 도입부)을 앞에 붙여 child 하나만 읽어도 뜻이 통하게 했다. 문장 중간은 자르지 않는다.
- 임베딩 입력에는 `법령명 > 장 > 조(제목) 제N항 …` 맥락을 앞에 붙였다.
- 결과: child 186개, 길이 중앙값 135자, 최대 517자.

### 검색·답변
- 임베딩 `text-embedding-3-small`(dense, cosine) + sparse(어절·글자 bigram·조문참조 토큰을 해시, Qdrant IDF)를 **RRF로 합치는 hybrid** 검색.
  한국어 형태소 분석기 없이 조사 변형(`인공지능을/이`)과 `제6조` 같은 정확 매칭을 모두 다루려는 선택이었다.
- LLM listwise rerank → 조(parent) 단위로 묶어 컨텍스트 구성 → 구조화 출력으로 답변 + 인용 조문 검증.
- 이 시점의 검증은 **질문 5개를 직접 눈으로 본 것**이 전부였다(정의·과태료·조문 직접 지정·열거·범위 밖).

### 입력을 API(XML)로 전환
국가법령정보 Open API(`lawService.do`, `type=XML`)를 받게 되어 입력을 바꿨다.
- 응답에 조·항·호·목이 **태그로 이미 나뉘어** 있어 접두어 추측이 필요 없다. 가지조문·가지호는 `조문가지번호`·`호가지번호` 필드, 장·절은 `조문여부=전문` 단위다.
- 부칙이 최신 1건이 아니라 3건 전부 제공된다.
- HWPX와 교차 대조해 누락 0줄, 조/항/호/목 개수가 동일함을 확인한 뒤 HWPX 파서는 제거했다. child는 188개가 됐다.

## 3. 걱정된 점

청킹 구조 자체는 점검에서 문제가 없었다(원문 말단 373개가 모두 child에 들어 있고, 법률 단위대로 잘렸다).
다만 "이 쪼개기가 **검색에 좋은지**"는 질문 5개로는 알 수 없었고, 점검 중 세 가지가 마음에 걸렸다.

1. **같은 조의 child가 검색 상위를 차지한다.** "고영향 인공지능 영역" 질문에서 상위 20개 중 9개가 제2조의 목 child였다.
   목마다 4호 도입부가 똑같이 붙어 있어 서로 비슷한 점수를 받는 탓이다. 다른 조문이 들어올 자리가 줄어든다.
2. **짧은 항은 다른 항을 가리키면 뜻이 불완전하다.** 70자 미만 child가 16개 있었고, 제7조⑧ "간사위원은 제4항제3호의 위원이 된다"는
   제4항제3호가 무엇인지 child 안에 없다.
3. **500자라는 기준은 임의로 정한 값**이고, 최선인지 비교한 적이 없다.

①은 한 질문에서 직접 본 현상, ②는 구조상 확실한 한계, ③은 미검증이었다. 어느 것이 실제로 검색 품질을 해치는지는 **측정이 필요**했다.

## 4. 측정 방법

### 골든셋 (`eval/golden_set.jsonl`, 43문항)
| 유형 | 문항 수 | 예 |
|---|---|---|
| def (정의) | 5 | 생성형 인공지능이 법적으로 뭘 뜻해? |
| list (열거) | 8 | 고영향 인공지능을 제공하는 사업자는 어떤 조치를 해야 해? |
| short (짧은 항) | 7 | 위원장이 자리를 비우면 누가 직무를 대신해? |
| xref (다른 항 참조) | 3 | 위원회 간사는 어떤 사람이 맡아? |
| direct (조문 지정) | 3 | 제17조의2 내용 알려줘 |
| duty (의무·제재·권리) | 13 | 과태료를 내야 하는 경우는 어떤 때야? |
| crowd (독점 유발) | 2 | 고영향 인공지능을 쓰는 사업자가 지켜야 할 의무를 알려줘 |
| oos (범위 밖) | 2 | 대한민국의 수도는 어디야? (정답 없음, 검색 지표에서 제외) |

질문은 조문 문구를 그대로 베끼지 않고 일상어로 썼다. 정답은 `{조, 항}` 목록이며, 정답 조·항이 실제 존재하는지 코드로 검증했다.

### 지표 (정답이 있는 41문항 평균)
- `cand@20`: 상위 20개 child 안에 정답 조가 있는 비율 (rerank가 보게 될 후보에 정답이 있는가)
- `art@3`: 중복을 뺀 상위 3개 조 안에 정답 조가 있는 비율
- `mrr`: 정답 조가 처음 나오는 조 순위의 역수
- `child@10`: 정답이 항까지 지정된 문항에서 상위 10 child 안에 그 항의 child가 있는 비율
- `div`: 상위 20 child가 담은 서로 다른 조의 수 (낮을수록 같은 조가 자리를 독점)
- 보조 분석: 정답 항을 덮는 child의 **순위와 길이**(조 전체를 담은 child도 덮는 것으로 침)

### 비교한 변형 (임시 컬렉션 `eval_*`에 각각 적재, 끝나면 삭제)
| 이름 | 내용 |
|---|---|
| base | 기존: 500자, 상한·참조 풀기 없음 |
| cap2 / cap3 | 검색 결과에서 한 조당 child를 최대 2개 / 3개로 제한 (`max_per_parent`) |
| refs | child가 가리키는 같은 조의 항·호 본문, 다른 조의 제목을 **임베딩 입력에만** 덧붙임 (화면에 보이는 원문·인용은 그대로, 40개 child에 적용) |
| refs+cap2 / refs+cap3 | 위 둘을 함께 |
| c300 / c800 / c1200 | child 크기 기준을 300 / 800 / 1200자로 |

### 5-3. 걱정별 해석

아래에서 "조 순위"는 정답 조가 처음 나오는 순위(5-1의 `mrr`의 바탕), "child 순위"는 정답 항을 덮는 child의 순위(5-2)다. 서로 다른 지표라 섞어 읽지 않는다.

**① 독점 → 조당 상한: 효과 없음 (채택 안 함)**
- 독점은 실제로 있었다. 상한을 두면 서로 다른 조의 수가 10.2 → 14.4(cap2)로 늘었다.
- 하지만 **독점이 정답을 놓치게 하지는 않았다.** 모든 변형에서 `cand@20`이 1.000이다. 정답 조는 항상 후보 20개 안에 있었다.
- `art@3`·`mrr`은 그대로고, `child@10`은 오히려 소폭 하락했다(0.625 → 0.594).
- 5-2에서 순위가 좋아 보이는 것(1.53 → 1.35)은 같은 조의 형제 child를 걷어내 순위가 앞당겨지는 **수치상 효과가 섞여 있어** 품질 개선으로 보지 않았다.

**② 짧은 항의 참조 → 참조 풀기: 효과 없음, 일부 악화 (채택 안 함)**
- 노린 `xref` 문항이 좋아지지 않았다. 정답 항을 덮는 child의 순위가 q09(간사) 2위 → 2위, q10(임기) 1위 → 1위, q16(비밀 누설) 2위 → 2위로 **전혀 변하지 않았다.**
- 오히려 정답 **조**의 순위가 나빠진 문항이 있다: q06(고영향 영역 열거) 4위 → 7위, q16·q27·q30 1위 → 2위. 전체 `mrr`도 0.911 → 0.884로 내려갔다.
- 원인은 확인하지 못했다. **추정**으로는, 가리키는 항의 본문을 덧붙이면 child 고유의 의미가 희석돼 그 항의 주제 쪽으로 끌려가는 것으로 보인다.
- 실제로 참조 풀기가 필요 없는 정황도 있다. 최종 답변 단계에서는 LLM이 **조 전체(parent)** 를 받기 때문에,
  "위원회 간사는 누가 맡아?"에 "제7조제8항, 제4항제3호의 위원 = 대통령비서실의 수석비서관"으로 풀어서 답했다.

**③ 500자 기준 → 300자가 가장 안정적 (채택)**
- `art@3` 0.951 → 0.976, `mrr` 0.911 → 0.929. 정답 조의 순위는 q35(설명 요구권)가 4위 → 1위로 올랐고, 나머지 문항은 같거나 변하지 않아 **나빠진 문항이 없다.**
  정답 항을 덮는 child의 순위도 q09(간사)·q16(비밀 누설)이 2위 → 1위로 올랐다.
- 정답 child의 평균 길이가 224자 → 147자로 짧아져 **더 정확한 위치**를 가리킨다.
- `div`가 낮아진 것(8.2)은 child가 잘게 나뉘어 한 조가 여러 칸을 차지한 결과인데, 정답 순위는 오히려 좋아졌다.
- 800자·1200자는 `child@10`이 0.312·0.031로 급락한다. 큰 기준에서는 조 전체가 child 하나가 되어 **항 단위 child가 사라지기 때문**이다.
  이 지표는 청크 크기와 구조적으로 얽혀 있어서, 1200자의 낮은 점수를 "검색이 나쁘다"로 읽으면 안 된다. 대신 1200자는 정답 child가 평균 591자로, 근거 위치가 뭉뚱그려진다.
- 5-2에서 `c1200`의 순위(1.25)가 가장 좋아 보이는 것도 조 전체가 child 하나라서 생기는 착시다.

## 6. 반영한 내용과 남은 한계

### 반영
- `rag/chunker.py`의 `DEFAULT_MAX_CHARS`를 **500 → 300**으로 변경. 운영 컬렉션을 다시 적재했다(child 271개, 길이 중앙값 123자·p90 221자·최대 378자, 300자 초과는 4개).
- 운영 컬렉션 재평가 결과가 실험의 `c300`과 일치했다(art@3 0.976, mrr 0.929, child@10 0.875). `div`만 8.15로 실험(8.24)과 소수점 차이가 났고 원인은 확인하지 못했다.
- 조당 상한(`max_per_parent`)과 참조 풀기(`resolve_refs`)는 **기본값을 꺼 둔 옵션**으로 남겼다. 실험을 다시 돌릴 수 있고, 켠다고 해서 지금은 이득이 없다.

### 한계 (결과를 읽을 때 주의)
- **표본이 작다.** 정답이 있는 문항이 41개라 문항 1개가 약 2.4%p다. `art@3`의 0.951 ↔ 0.976은 한 문항 차이이고, 변형 간 차이는 대체로 문항 1~2개 수준이다.
  "300자가 확실히 낫다"가 아니라 "해당 문항에서 나빠진 것이 없고 몇 개가 좋아졌다"가 정확한 표현이다.
- **골든셋의 정답을 조문을 읽고 한 사람(AI)이 만들었다.** 라벨 작성자의 편향이 들어갈 수 있다. 사람이 문항을 추가·검수하면 신뢰도가 올라간다.
- **`cand@20`이 전 변형에서 1.000으로 포화**되어, 이 골든셋으로는 후보 회수 단계의 차이를 구분하지 못한다. 변별은 `art@3`·`mrr`·순위에서만 나왔다.
- **rerank까지 거친 최종 컨텍스트 지표(`ctx`)는 측정하지 않았다.** 변형마다 문항당 LLM 호출이 필요해 비용이 커서 뺐다(`--rerank` 옵션은 준비돼 있다).
  rerank가 단점을 보완했을 가능성이 있어, 위 결론은 "rerank 이전 검색 단계" 기준이다.
- **300자 미만은 시도하지 않았다.** 가장 작은 값이 최고였으므로 최적점이 더 아래(예: 200~250자)일 수 있다. 다음 실험 후보다.
- 조문 간 참조 해소, 시행령 포함, 부칙 노이즈는 이번 범위가 아니다([rag_design.md](rag_design.md)의 알려진 제한 참고).

## 7. 평가 중 겪은 문제: 429 (분당 호출 제한)

- **증상:** sweep이 `RateLimitError 429 (분당 30회)`로 반복 실패했고, 한 번은 첫 변형도 끝내지 못했다.
- **원인(확인됨):**
  1. 질문 43개와 인덱싱 배치를 개별 호출해서 분당 제한에 걸렸다.
  2. OpenAI SDK가 429를 받으면 **자체 재시도(기본 2회)** 를 하고, 이것도 호출 횟수에 잡혀 제한을 스스로 채웠다. 거기에 직접 만든 재시도가 겹쳤다.
  3. 이전 시도의 평가 프로세스가 **남아 있어 두 개가 동시에** 돌았다. PID 파일에 bash 래퍼의 PID를 저장해, 종료 명령이 실제 python을 죽이지 못했다.
- **수정:** 평가용 임베딩 클라이언트에 `max_retries=0`을 주고 재시도는 래퍼 한 곳에서만 하며, 질문을 한 번에 임베딩하고, 인덱싱 배치를 64로 키우고, 임베딩을 디스크 캐시(`data/processed/eval_embed_cache.json`)에 저장해 중간에 실패해도 이어 받게 했다.
  이후 분석·재적재는 캐시만으로 **API 호출 0회**로 할 수 있었다.
- **재발 방지:** 백그라운드 작업은 `$!`가 가리키는 실제 프로세스 PID를 확인해서 종료하고, 새로 시작하기 전에 같은 작업이 남아 있는지 먼저 본다.

## 8. 재현

```bash
uv run python -m rag.pipeline parse            # 법령 XML → Canonical JSON (캐시 사용, --refresh 로 API 재조회)
uv run python -m rag.pipeline ingest --recreate # 청킹(기본 300자) → 임베딩 → Qdrant
uv run python -m eval.evaluate                  # 운영 컬렉션 평가 (질문 임베딩 호출만 필요)
uv run python -m eval.evaluate --sweep          # 변형 비교 (임시 컬렉션을 만들고 지운다)
uv run python -m eval.evaluate --sweep --only base,c300 --rerank   # rerank 포함 (LLM 호출 발생)
```

평가를 돌리려면 `.env`에 `LLM_API_KEY`, `LLM_BASE_URL`이 있어야 하고, 법령을 API에서 새로 받으려면 `LAW_API_OC`도 필요하다.

## 9. 데이터 처리 검증 (원문 보존율·ID 충돌)

전처리(XML 파싱, 정규화, 청킹)에서 필요한 텍스트가 빠지거나 덮어써지지 않았는지 코드로 확인한다(`uv run python -m eval.evaluate --report`의 첫 블록, API 호출 없음).

| 확인 | 결과 |
|---|---|
| 원본 XML → 정규화 JSON 보존율 (조·항·호·목 본문 373개 단위) | **1.0000** |
| 정규화 JSON → child 청크 보존율 | **1.0000** |
| 정규화 JSON → parent(조 전체) 보존율 | **1.0000** |
| `chunk_id` 충돌 / Qdrant `point_id` 충돌 | **0 / 0** |
| Qdrant 저장 점 수 / 청크 수 | **271 / 271** (누락 0) |

보존율은 글자 수 기준이고, 번호 접두어(`제1조(…)`, `①`, `1.`, `가.`)와 개정 표기(`<개정 …>`)는 제외하고 본문만 비교한다.
